## Choose by desired outcome

| You need to | Start with | Completion evidence |
| --- | --- | --- |
| Learn the daily file cycle | [Work with managed files](/docs/cli/daily-workflow) | A second checkout hydrates the committed file |
| Onboard collaborators | [Share a repository](/docs/cli/guides/sharing-repositories) | Each collaborator resolves credentials and reads the same ref |
| Move from Git Large File Storage (LFS) | [Migrate from Git LFS](/docs/cli/guides/migrating-from-lfs) | Pointer history and required large objects survive the cutover |

| Run Crab in automation | [Integrate CI/CD](/docs/cli/guides/ci-cd-integration) | A clean runner fetches and hydrates only its declared working set |

## Keep command reference separate

Tutorials explain ordering, safety boundaries, and verification. Reference pages list accepted syntax, flags, defaults, and output contracts.

If you already know the operation, use the [CLI command index](/docs/cli/reference). If you need to understand why an operation exists, start with the relevant conceptual or workflow page before copying commands.

## Include failure proof in rehearsals

Run migration and automation guides against a disposable repository before changing production state. Capture both the successful path and one expected failure, such as missing credentials, unavailable remote data, or a non-fast-forward ref.

The failure should stop before publication and retain an actionable error. This proves that the workflow does not report success while leaving its data closure incomplete.

Keep the rehearsal commands, expected exit status, and verification artifact in
the repository or CI configuration so the same safety boundary can be tested
after a Crab upgrade.

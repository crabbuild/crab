# Fetching Updates

Fetching verifies selected Crab files into a discard sink and retains decoded
xorb ranges and metadata without changing the worktree. Those ranges warm
explicit hydrate, filter smudge, mount, and worktree-prefetch reads. Fetch followed by
offline explicit `crab hydrate` is not yet a supported guarantee.

## Why Fetch Separately?

Hydration downloads chunks on demand — when you ask for a specific file, Crab fetches its chunks from cloud storage. This works well for small numbers of files, but for large batches it means hydration speed is limited by download latency.

Fetching decouples the download from the reconstruction:

- **Pre-warm checkout or mount reads** — Download selected ranges on a fast connection before those compatible paths need them.
- **Avoid worktree changes** — Verify remote content without replacing pointer files.
- **CI optimization** — Fetch objects once at the start of a pipeline, then hydrate selectively in each job.
- **Warm dedup metadata** — Synchronize the persistent local chunk index after fetch unless disabled.

## How It Works

When you fetch, Crab:

1. Resolves Crab pointer blobs from HEAD/index, or local refs with `--all`.
2. Applies include/exclude patterns to repository paths.
3. Selects the configured primary or replica.
4. Reconstructs each selected file through the verified shard/xorb read path,
   discarding output after hash and size validation.
5. Synchronizes the persistent local chunk index unless
   `--no-sync-chunk-index` is set.

The local cache lives at `~/.cache/crab/` by default; `$CRAB_CACHE_DIR` overrides its root.

## Selective Fetching

You don't have to fetch everything. For large repositories, fetch only what you'll need:

```bash
# Fetch objects for model files only
crab fetch --include '*.safetensors'

# Fetch everything except training data
crab fetch --exclude 'data/train/*'

# Fetch objects for all branches, not only HEAD
crab fetch --all
```

## Fetch and Later Reads

Fetch can warm compatible checkout and mount reads:

```bash
# Download objects while on fast network
crab fetch --include 'models/**'

# A later checkout or mount read can reuse decoded ranges
git checkout feature/model-update
```

Explicit `crab hydrate` now uses the same cache policy. Warm payload reads may
still require metadata or authorization requests; do not infer fully offline
access from cached ranges alone. Cross-process and provider qualification is tracked in
[Plan 017](https://github.com/crab-build/crab/blob/main/plans/017-local-cache-read-hardening.md).

## Cache Management

The fetch cache persists across operations and repositories. Over time it can grow large. Manage it with:

- `crab cache stats` — See the reported range/object cache sizes and counts
- `crab prune` — Evict oldest cache objects until cache budgets are satisfied
- `crab cache clean` — Clear the entire cache

Configure the cache budget in `.crab/local.toml`:

```toml
[cache]
max_bytes = 10737418240
```

The default is 10 GiB. Unified accounting and maintenance remain Plan 017 work,
so this setting does not yet prove a total disk ceiling across all families.
Unknown `[cache]` keys such as `max_size` are rejected.

Local cache data can reconstruct private repository content. Keep it private
to one operating-system user; use the authenticated remote cache service for
team reuse.

## Fetch vs. Pull

`crab fetch` is not the same as `git pull`:

| Operation | Moves | Changes working files |
| --- | --- | --- |
| `git fetch` | Git commits, trees, and pointer blobs | No |
| `git pull` | Git objects and the selected branch integration | It can update pointers through checkout or merge |
| `crab fetch` | Crab shards and xorbs into local cache | No |
| `crab hydrate` | Reconstructed file bytes into the working tree | Yes |

You typically need both: `git pull` to get the latest pointers, then `crab fetch` + `crab hydrate` to get the actual file content.

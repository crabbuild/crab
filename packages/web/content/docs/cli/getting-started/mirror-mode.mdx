# Mirror Mode (GitHub + Crab)

Mirror mode keeps GitHub (or GitLab) as the collaboration control plane for pull requests, reviews, branch protection, CI, issues, and webhooks. Crab is a second Git remote backed by object storage and stores both the pushed Git graph and large-file data.

## Data Flow

![Mirror mode data flow — pre-push hook sends large files to S3, then git push sends pointer blobs to GitHub.](./mirror-mode-flow.svg)

When collaborators pull from GitHub, the `post-checkout` hook hydrates pointer files from the Crab remote automatically.

## Setup: Repository Owner

### Prerequisites

- A GitHub/GitLab repo with an `origin` remote already configured
- An S3/GCS/Azure bucket for Crab storage
- Cloud credentials configured (AWS CLI, gcloud, or az)

### Initialize

```bash
cd my-project
crab init --mirror=origin crab://my-bucket/my-repo
```

This command:

1. Validates that the `origin` remote exists
2. Adds a `crab` remote pointing to your bucket
3. Installs `pre-push`, `post-checkout`, and `post-merge` hooks
4. Generates `crab.toml` with a `[mirror]` section
5. Run `crab setup` to auto-track large file patterns in `.gitattributes`

### Push the configuration

```bash
crab setup
crab ship . -m "enable crab for large files"
```

Now `crab.toml` is on GitHub. Collaborators will inherit the mirror setup.

## Setup: Collaborator

After cloning from GitHub:

```bash
git clone git@github.com:team/project.git
cd project
crab init
```

Running `crab init` with no URL detects the `[mirror]` section in `crab.toml` and automatically:

- Adds the `crab` remote
- Installs mirror hooks
- Hydrates files per `[hydrate]` settings

If the collaborator previously ran `crab install --global`, the global filter
driver can activate from `crab.toml`, but still run `crab init` when the repo
needs the mirror remote and hooks installed locally.

## How Hooks Work

### `pre-push` — Before pushing to GitHub

```bash
#!/bin/sh
# Crab mirror: publish the exact pre-push ref batch
crab mirror-pre-push "$@" || exit $?
```

The development-line hook reads Git's complete stdin batch and publishes its
exact object IDs and destination refs to Crab before allowing the GitHub
push. It handles differently named branches, annotated tags, revision
expressions, rewrites, and explicit deletions; it does not substitute the
current branch. Empty batches do nothing. Direct `crab://` pushes skip mirror
publication to avoid recursion.

The guard validates the batch, resolves the configured destination, and
captures an independent Crab expected-old ref snapshot. A Crab ref that differs
from both Git's advertised old value and the proposed new value blocks the
whole batch. An unchanged snapshot permits an explicitly requested rewrite;
a concurrent Crab writer still causes its lease check to fail. Unmentioned
refs are retained. After publication, the guard verifies reachable Crab
pointer bytes at origin and checks the resulting refs. A failure prevents
the collaboration push but does not undo a Crab commit.

The hook accepts SHA-1 publication batches up to 16 MiB. Malformed input and
duplicate destinations fail before publication. The supplied collaboration
URL must match the configured source's push URLs; the Crab remote must have
exactly one push URL. Fix mismatched configuration rather than bypassing the
guard. Re-run `crab init` to update a recognized older Crab hook.

These changes are not yet a release-qualified guarantee across all Git
versions, platforms, and providers. Continuous snapshot protection against
GC and the remaining failure matrix are still qualification work. Run the
remote integrity check below and retain the evidence for your environment.

The two remote updates are not one distributed transaction. Crab can be ahead
if its push succeeds and GitHub later rejects the push. Server-side merges,
bots, and clients without the hook can also advance GitHub without advancing
Crab. Retry to converge and monitor ref divergence.

### `post-checkout` — After switching branches or cloning

```bash
#!/bin/sh
# Crab mirror: hydrate pointer files after checkout
crab hydrate . 2>/dev/null || true
```

Materializes pointer files so you see real content after branch switches. Non-fatal on failure.

### `post-merge` — After pulling or merging

```bash
#!/bin/sh
# Crab mirror: hydrate after merge/pull
crab hydrate . 2>/dev/null || true
```

Same behavior as post-checkout, triggered by `git pull` and `git merge`.

### LFS and existing hooks

`crab lfs install` and mirror installation compose into one input owner:

```bash
#!/bin/sh
# Crab LFS: publish objects before refs
# Crab mirror: publish the exact pre-push ref batch
crab mirror-pre-push --lfs "$@" || exit $?
```

Both guards use the same decoded object IDs. LFS uploads use the configured
Crab destination, not the GitHub/GitLab URL. Either install order produces
this hook; uninstalling LFS preserves the mirror guard.

Installation honors `core.hooksPath` and is idempotent for recognized Crab
hooks. An unknown/custom pre-push hook is left unchanged and installation
fails with manual-composition guidance. Do not simply append two commands
that both read stdin: the first can consume the batch and leave the second
with nothing to check. A manual wrapper must retain and supply the complete
batch to every input consumer and propagate every failure. Status only
attests exact recognized Crab hook contents, not arbitrary custom wrappers.
Post-checkout and post-merge installation preserves adjacent custom commands.

## Checking Status

```bash
crab status
```

`crab status` reports local configuration, pending staging work, and the
installed pre-push guard. It deliberately does not call either provider or
claim that the remotes are healthy. Run the integrity check for authoritative
remote state:

```bash
crab mirror origin crab://my-bucket/my-repo --check
```

The result distinguishes equal refs, source-ahead refs, Crab-ahead recoverable
state, true divergence, unavailable observations, missing hooks, and missing
pointer recipes or data.

### Enforce pointer availability in CI

Make the collaboration remote URL available to the job, configure Crab
credentials, and run:

```bash
crab mirror "$COLLABORATION_REMOTE" crab://my-bucket/my-repo \
  --check --ci --json > mirror-check.json
```

The command exits nonzero if collaboration refs and Crab refs differ, any
source-reachable Crab pointer lacks its committed recipe or immutable data,
origin bytes fail hash/length verification, or verification is incomplete.
The check reads reachable large-file content directly from origin; allow for
that time and provider cost. Retain `mirror-check.json` as the status-check
artifact. Required CI can block a protected merge or deployment; it cannot
undo a ref already accepted by GitHub/GitLab.

### Reconcile without implicit deletion

Generate, review, and then apply an immutable plan:

```bash
crab mirror origin crab://my-bucket/my-repo \
  --check --write-plan mirror-plan.json
crab mirror origin crab://my-bucket/my-repo \
  --apply-plan mirror-plan.json
```

Plans only publish source-ahead refs to Crab. Crab-ahead common refs and true
divergence remain blocked until an operator chooses the source of truth.
Destination-only refs are retained unless `--allow-delete-refs` is passed
both while writing and applying the reviewed plan. Apply revalidates the plan
digest, targets, ref snapshots, and pointer data; a stale plan fails instead
of guessing.

## Configuration

The `[mirror]` section in `crab.toml`:

```toml
[mirror]
origin_remote = "origin"    # GitHub/GitLab remote name
crab_remote = "crab"        # Crab storage remote name
```

## When to Use Mirror Mode

**Use mirror mode when:**
- Your team uses GitHub/GitLab for code review and CI
- You have large files (models, datasets, assets) that bloat git
- You want PRs to show pointer diffs, not binary blobs
- You need deduplication and lazy checkout for large files

**Use standard mode when:**
- Crab is your only remote (no GitHub/GitLab)
- You don't need code review on a separate platform
- You want the simplest possible setup

## Production Team Posture

- Keep GitHub/GitLab canonical for collaboration and policy. Crab does not
  provide pull requests, branch protection, merge queues, CI, issues, or
  webhooks.
- Keep Crab/object storage canonical for large data, using workload identity
  and least-privilege bucket policy instead of shared static keys.
- Install hooks on every developer and automation clone, then enforce pointer
  availability in CI because client hooks are bypassable.
- Existing `crab mirror SOURCE DESTINATION` invocations remain a one-way,
  destructive full-ref sync. New automation should use `--check`, an immutable
  plan, and `--apply-plan`; never schedule either form in both directions.
- Before using Crab as the sole Git backbone, qualify multi-node storage
  failures and prove monitoring, backup restore, RPO, and RTO in your own
  environment.

## Troubleshooting

### Hooks not firing

Verify hooks are installed:

```bash
git rev-parse --git-path hooks/pre-push
crab status
```

Re-run `crab init` to reinstall if missing.

### Hydration fails after pull

Check credentials and remote connectivity:
```bash
crab doctor
git remote get-url crab
```

### Push rejected by GitHub (file too large)

This means the pre-push hook didn't fire. Check that:
1. The hook file exists and is executable
2. `crab` is on your PATH
3. Run `crab init` to reinstall hooks

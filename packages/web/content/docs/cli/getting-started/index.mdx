# What is Crab?

Crab extends Git with a separate data path for large files. Git commits small pointer blobs, while Crab stores chunked file content through an object-store adapter.

## What Crab changes

Git remains responsible for commits, trees, branches, tags, and small file content. Crab manages files selected by `.gitattributes` rules that use `filter=crab`.

When you add a managed file, Crab divides its bytes into content-defined chunks. It hashes those chunks, reuses durable chunks when possible, and stages any new bytes locally. Git receives a pointer that identifies the complete file version.

Push publishes both parts of the repository. Crab uploads missing data objects and metadata before it advances the Git ref. If the data closure is incomplete, publication fails and existing readers keep the previous ref.

## Create one repository

Install Crab, configure a storage location, then publish the first commit:

```bash
curl -fsSL https://crab.build/install.sh | bash
mkdir model-repository
cd model-repository
crab configure s3://example-bucket/model-repository
crab ship . -m "Initial repository"
```

`crab configure` initializes Git when needed, writes Crab configuration, registers the filter driver, and scans for large-file patterns. `crab ship` combines add, commit, and push for a local change.

Use the individual commands when you need to inspect each boundary:

```bash
crab add models/weights.safetensors
git diff --cached
git commit -m "Add model weights"
crab push
```

## Follow one file through the system

The same file has different representations at each boundary:

| Boundary | Representation | Authority |
| --- | --- | --- |
| Working tree before add | Full local bytes | Local filesystem |
| Git index and commit | Crab pointer blob | Git history |
| Crab staging | Recipe and any new chunks | Publishing client |
| Remote data path | Immutable xorbs, shards, and file index | Object storage |
| Hydrated working tree | Reconstructed full bytes | Verified recipe and chunk hashes |

Hydration reconstructs the file named by the pointer. It does not select a newer version by path. The commit still determines the exact file identity.

## Choose a storage URL

Provider-prefixed URLs let `crab configure` infer credential discovery:

| Provider | Configuration example |
| --- | --- |
| Amazon S3 | `crab configure s3://example-bucket/repository` |
| Google Cloud Storage | `crab configure gs://example-bucket/repository` |
| Azure Blob Storage | `crab configure azure://example-container/repository` |
| S3-compatible storage | `crab configure crab://example-bucket/repository --provider s3` |

Crab normalizes provider-prefixed inputs to a `crab://` Git remote. The repository path isolates its metadata and objects inside the bucket or container.
These entries describe adapter syntax, not current release qualification.

## Decide what to materialize after clone

A default Crab clone can leave managed files as pointers. Hydrate the working set required by the current task:

```bash
crab clone crab://example-bucket/model-repository
cd model-repository
crab hydrate 'models/*.safetensors' data/evaluation/**
```

Use `crab hydrate --all` when the machine needs the complete working tree. Use `crab dehydrate` after a task to replace clean hydrated files with pointers and reclaim local disk space.

## Need Git LFS compatibility?

Most new Crab repositories should use Crab-native tracking with `crab track`.
Choose **Crab LFS** when the repository already contains standard LFS pointers
or a tool requires `filter=lfs` and `git lfs` commands. Crab runs the filters and
transfer agent on each client and writes directly to your object-storage
bucket—there is no Git LFS server or gateway to deploy.

```bash
crab init --storage-provider s3 crab://team-bucket/model-repository
crab lfs install --local
crab lfs track '*.safetensors'
git add .gitattributes
git commit -m "Track model files with Crab LFS"
git push origin main
```

Start with [Use Crab LFS directly](/docs/cli/getting-started/crab-lfs) when
you need standard LFS pointers. It explains the direct-storage route, daily
commands, fresh-clone verification, and the boundary between `crab lfs` and
Crab-native tracking.

## Check whether Crab fits the repository

Crab is a strong fit when large files change across versions, clients need different working sets, and the team can operate cloud credentials. Deduplication depends on encoded byte overlap, so encrypted or recompressed versions may reuse little data.

Crab does not replace code review, issue tracking, or every forge feature. It owns Git-compatible transport and the large-file data path.

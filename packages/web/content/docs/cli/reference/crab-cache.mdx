# crab cache

Manage the local chunk cache.

## Synopsis

```bash
crab cache stats [--json]
crab cache verify
crab cache clean
```

## Description

`crab cache` manages the local chunk cache that stores previously downloaded
xorb data. The cache speeds up repeated hydrations by avoiding redundant
downloads from cloud storage.

For conceptual background, see [Local Cache](/docs/cli/storage/local-cache).

Clean, verify, and [`crab prune`](/docs/cli/reference/crab-prune) reject a cache
root that resolves to the filesystem root, home directory, current directory,
or an ancestor of the current directory. The corresponding `crab optimize cache`
commands use the same safeguard. Missing cache roots are left missing; private
payload I/O independently rejects symlinked or non-private roots.

## Subcommands

### stats

Show the effective root and shared byte budget, observed logical file lengths,
allocated disk blocks, and per-family counts/availability. Counts include
chunks, decoded ranges, xorbs, shards, manifests, stages, indexes, hints, bloom
files, databases and side files, temporaries, and retained/unknown files.
Directory allocation has a separate row. Catalog row totals, reserved bytes,
and the last recorded maintenance time are separate from filesystem usage.

Inspection leaves missing paths missing and does not initialize the writable
range cache, verify payload bodies or unrelated index bodies, or repair unsafe
files. The catalog uses a non-mutating SQLite transaction. The shard-hint
database is checked read-only for its exact schema, hash row shapes, global row
bound, and SQLite `quick_check`. Existing WAL data is read without checkpointing
or creating recovery files. Busy, corrupt, or unsafe databases are reported
unavailable, not empty. A main file can need OS write permission for SQLite's
exclusive byte-range lock even though SQL/VFS data writes are denied.

Errors in one family do not hide independent healthy families. Affected rows
are partial; their measured bytes are lower bounds. At most 64 issue details
are retained, with additional counts reported. Stats exits unsuccessfully if
an inspection is unavailable. Invalid configuration fails without substituting
defaults. Over-budget usage is reported but is not itself an inspection error.

`--json` emits one `cache.stats` version `1.0` envelope. Partial reports remain
in `data` with a nonzero exit; failures before inspection use the normal `error`
envelope. `crab optimize cache stats` uses the same report and option.

Retention is unlimited by default. Text reports show `budget: unlimited`;
JSON uses `budget_bytes: null` for no configured cap, not unknown usage.
Numeric caps remain byte counts. Unlimited reports are not over budget, but
unsafe paths and incomplete inspections still produce diagnostics and failure.

The streaming walk is not an atomic snapshot or a full integrity verification.
Allocation covers linked entries, not unlinked open files; reservations are
separate and shared filesystem extents may be counted more than once. An
incomplete scan with a configured cap reports unknown over-budget state unless observed allocation
already exceeds the budget. Physical reporting is not proof of all-family
budget enforcement. No persistent cache hit rate is recorded. Cancellation is
checked during traversal; SQLite waits/aggregation still have separate bounds.

```bash
crab cache stats
crab cache stats --json
crab optimize cache stats --json
```

### clean

Remove recognized private cached payloads to free disk space.

```bash
crab cache clean
```

Unknown files/subtrees, live workspaces, mirror repositories, retained profiles,
databases and side files, and unpublished temporaries are preserved. Active
readers and concurrent publishers are skipped. The command reports actual
removals plus retained, busy, and unsafe entry counts; retained subtrees count
once without inspecting their contents. Empty directories remain.

The current cache subcommands do not add command-specific selection flags;
use `crab cache <command> --help` for global logging options.

### verify

Validate content-addressed chunks and shards, xorb payload digests and decoded
chunks, and range lengths, offset headers, CRCs, and applicable chunk identities.
Verification streams recognized private entries and holds locks through each
check and removal. Unknown files and busy entries are retained and excluded
from checked totals. Operational I/O failures fail the command, rather than
authorizing deletion. SQLite/root ownership and full reservation protection
remain hardening work. Neither
`crab cache clean` nor `crab optimize cache clean` currently exposes a dry-run flag.

## Remote Cache Service

The `crab cache` command manages your **local** disk cache — a per-machine store of previously downloaded chunks. For teams, Crab also supports an optional **remote cache service** (`crab-cache-server`) that shares cached objects across all developers and CI runners.

### How They Relate

| | Local Cache | Remote Cache Service |
|---|---|---|
| **Scope** | Single machine | Entire team / org |
| **Storage** | Your local disk (`~/.cache/crab/`) | Dedicated server with NVMe |
| **Population** | Filled on fetch/hydrate | Filled on fetch + push warming |
| **Eviction** | Unlimited by default; optional cap and explicit cleanup | Background evictor with high/low watermarks |
| **Setup** | Zero config (automatic) | Requires server deployment |

When both are configured, Crab checks the local cache first. On a local miss, it queries the remote cache service before falling back to cloud storage. This means the first developer to fetch a file warms the remote cache, and every subsequent fetch across the team is served at network-local speed.

### Enabling the Remote Cache

Add the cache service URL to your Crab config:

```toml
[cache]
service_url = "https://crab-cache.internal:8443"
service_auth = "psk"
service_psk = "my-secret-key"
push_warming = true
```

With `push_warming = true`, newly pushed xorbs are sent to the remote cache immediately — teammates can hydrate without waiting for a cold-start download from S3.

For full deployment instructions, server configuration, and authentication setup, see the [Cache Service](/docs/cli/cache-service) guide.

# crab migrate

Inspect large-file history and convert DVC workflow state into Crab metadata.
The history-rewrite commands are currently dry-run only: non-dry-run requests
fail explicitly without changing the repository. Use `crab adopt` for the
supported working-tree cutover path.

## Synopsis

```bash
crab migrate <SUBCOMMAND> [OPTIONS]
```

## Subcommands

| Command | Purpose |
| --- | --- |
| `crab migrate info` | Report file types above a size threshold that would benefit from tracking |
| `crab migrate import` | Preview a large-file-to-pointer history migration; applying it is not yet supported |
| `crab migrate export` | Preview a pointer-to-full-file history migration; applying it is not yet supported |
| `crab migrate from-dvc` | Convert a `dvc.yaml` pipeline to `crab.yaml` |
| `crab migrate gc-fence` | Inspect or explicitly upgrade one quiesced coordination domain to schema 2 |

## Examples

Inspect large-file extensions:

```bash
crab migrate info
crab migrate info --above 10485760 --top 5
```

Preview a prospective history rewrite:

```bash
crab migrate import --include '*.bin' --include '*.safetensors' --dry-run
crab migrate import --include '*.bin' --everything --dry-run
```

Preview exporting selected pointer-backed files from history:

```bash
crab migrate export --include '*.bin' --dry-run
```

Convert a DVC pipeline:

```bash
crab migrate from-dvc --dir . --output crab.yaml
```

Use `--stdout` with `from-dvc` to inspect the converted YAML without writing a
file.

## GC coordination upgrade

Schema 2 binds GC writer epochs to a domain incarnation. Deleting and
recreating a fence can no longer reuse the identity sealed into a GC plan.
New domains use schema 2; existing schema-1 domains require explicit migration.
Older binaries, including v1.0.1, refuse the new fence. This is not a rolling
upgrade: stop **all** writers and sweepers sharing the physical domain first,
including protected services, maintenance jobs and other repositories using
the same global data domain.

1. With the previous binary, release all holders and resolve expired claims
   and quarantine. Migration refuses any remaining recorded holder or
   quarantine, including expired entries. Do not delete the fence to unblock it.
2. Inspect each exact repository and global domain separately:

   ```bash
   crab migrate gc-fence --remote crab://bucket/org/repo --domain org/repo
   ```

3. While every client remains stopped, apply the validated upgrade:

   ```bash
   crab migrate gc-fence --remote crab://bucket/org/repo --domain org/repo --apply --quiesced
   ```

4. Upgrade all clients before restarting them. Start a fresh GC plan; schema-1
   journals cannot resume under the new binary. Do not restore an old fence or
   journal as a rollback procedure. A data restore requires quiescence and a
   new GC inventory; arbitrary out-of-band restoration of coordination state
   cannot be detected reliably on unversioned storage.

Inspection performs no object writes. Apply uses one conditional update;
conflicts require reinspection. Reapplying an already upgraded domain changes
nothing. Migration changes only the selected fence, not Git refs, payloads or
other domains. Read-only use of an older binary is a separate compatibility
contract; it does not authorize older writers against upgraded domains.

Crab lets one Git repository contain source code, datasets, model weights, and media without forcing every file through one storage format. Ordinary files remain Git blobs. Tracked large files use Crab’s Xet-backed large-file path in object storage, while Git records a small pointer. This article starts with a working repository and then explains the architecture behind `crab add`, `crab push`, and `crab hydrate`.

## Start with a repository you can picture

Consider a machine learning project named `vision-search`. It contains code that Git already handles well and binary files that can grow by gigabytes.

```text
vision-search/
├── README.md
├── src/
│   └── train.py
├── models/
│   └── encoder.safetensors
└── datasets/
    └── captions.parquet
```

The repository needs one history. A commit should describe the exact combination of training code, model weights, and input data. Splitting the large files into a separate manual download process would weaken that connection.

Putting every byte into normal Git creates a different problem. A changed 8 GB model becomes another large Git blob, even when most of its bytes match the previous version. Clones and repository maintenance must account for every version of that blob.

Crab keeps the files in one commit while choosing a representation for each path:

| Path | Representation in Git | Large bytes |
|---|---|---|
| `README.md` | Complete Git blob | Already in Git |
| `src/train.py` | Complete Git blob | Already in Git |
| `models/encoder.safetensors` | Small Crab pointer | Chunks in object storage |
| `datasets/captions.parquet` | Small Crab pointer | Chunks in object storage |

The pointer records the file’s identity. It is not the file itself. A Crab-aware client reads that identity and reconstructs the original bytes when you need them.

## Create your first Crab repository

You need the Crab command-line interface, a cloud storage bucket, and credentials that can write to that bucket. Crab supports Amazon S3, Google Cloud Storage, Azure Blob Storage, and S3-compatible storage.

Create the directory and connect it to a bucket:

```bash
mkdir vision-search
cd vision-search
crab configure s3://company-repos/vision-search --no-auto-track
```

Replace `company-repos` with your bucket name. `crab configure` initializes Git when needed, writes Crab’s local configuration, registers the Git filter driver, and configures the remote.

The `--no-auto-track` option makes this example explicit. Register two large-file patterns after you copy the example files into the repository:

```bash
crab track '*.safetensors'
crab track 'datasets/**'
```

Crab writes these rules to `.gitattributes`. Commit that file with the project so every collaborator uses the same path selection.

Stage ordinary Git files first, then let `crab ship` stage the tracked files, commit everything, and push:

```bash
git add README.md src/
crab ship models/ datasets/ -m "Add training code, model, and caption data"
```

`crab ship` runs the remaining workflow:

1. It stages Crab pointers for the tracked model and dataset.
2. It creates a Git commit with your message.
3. It uploads missing Crab data and Git objects.
4. It updates the remote branch after its dependencies are durable.

The commit includes the ordinary files already staged by `git add`. This explicit split is useful for a first repository because each command shows which storage path it owns.

Run `crab status` when you want to inspect tracked files in the worktree:

```bash
crab status
```

The status view distinguishes full files, pointer files, and modified files. It does not replace `git status`; each command reports the state owned by its layer.

<TakeawayBox title="Your first working model">
You keep using a normal Git repository. Tracking rules select large-file paths. Crab stores their bytes efficiently and keeps a pointer in the same commit as your source code.
</TakeawayBox>

## Use the reviewable daily workflow

`crab ship` combines large-file staging, commit, and push. Use separate commands when you want to review the index, split work into commits, or control the destination branch.

Suppose you update both `src/train.py` and `models/encoder.safetensors`. Stage them together:

```bash
git add src/train.py
crab add models/encoder.safetensors
crab status
git diff --cached --stat
```

`git add` stages the complete source blob. `crab add` stages the model pointer and prepares its large-file data. The full model remains available at `models/encoder.safetensors` in your worktree.

Commit and publish the combined change:

```bash
git commit -m "Improve encoder training"
crab push origin main
```

You can also use `git push` with a `crab://` remote. Git invokes Crab’s remote helper for that URL. `crab push` exposes Crab-specific progress and uses the native concurrent upload path, so this article uses it in command examples.

The commands are familiar, but the storage work is different for each file. The next diagram shows the complete model before we inspect each stage.

## Learn the terms used in the diagrams

Crab’s Xet-backed path uses content-defined chunking and Xet’s reconstruction model. The architecture is easier to follow when each storage term names one job:

- **Git blob**: an immutable Git object that contains file bytes. Ordinary files use this representation directly
- **Pointer blob**: a small Git blob that records a tracked file’s hash, size, and format information
- **Chunk**: a byte range selected from a large file by content-defined chunking. Similar file versions can reuse matching chunks
- **Xorb**: an immutable compressed object that stores one or more chunks in cloud object storage
- **Shard**: metadata that maps a file’s ordered chunks to byte ranges inside xorbs

A Git ref is the final name in the process. For example, `refs/heads/main` identifies the commit currently visible as the `main` branch. Crab changes that ref only after every required Git object, xorb, and shard can be read.

The word **hydrate** means replacing a pointer in your worktree with the complete reconstructed file. **Dehydrate** means replacing a clean full file with its pointer to recover local disk space. Neither operation changes committed history.

## Crab extends Git instead of replacing it

Crab integrates at two extension points that Git already supports:

- A **filter driver** selects the blob Git records for a tracked path
- A **remote helper** transfers Git objects and refs for a `crab://` remote

Commands above those boundaries still behave like Git. You can branch, merge, commit, diff, fetch, and push. Commits still point to trees, trees still point to blobs, and refs still identify commits.

The difference is the meaning of a blob. An ordinary blob contains the file. A Crab pointer blob describes how Crab identifies the file.

```text
ordinary blob
└── exact file bytes

Crab pointer blob
├── pointer format version
├── full-file BLAKE3 hash
├── byte size
└── optional shard hint
```

Git can inspect repository structure without understanding Crab’s data plane. It can walk commits and trees, compare pointer blobs, and update refs. A Crab-aware client resolves a pointer when an application needs the full large file.

<TakeawayBox title="The ownership boundary">
Git owns history, path names, and commit identity. Crab owns reconstruction of the content named by a pointer. Object storage keeps both systems’ immutable data durable.
</TakeawayBox>

## Tracking rules select a representation per path

The split begins in `.gitattributes`. `crab track` writes entries like these:

```gitattributes
*.py          text
*.safetensors filter=crab diff=crab merge=crab -text
datasets/**   filter=crab diff=crab merge=crab -text
```

Paths without `filter=crab` stay on the ordinary Git path. Matching paths enter Crab’s large-file path. Files below Crab’s chunk threshold can remain normal content, so a broad pattern does not force every small file into chunk storage.

You can inspect or change the rules with commands that operate on the shared `.gitattributes` file:

```bash
crab track
crab track '*.onnx'
crab untrack '*.onnx'
```

Quote glob patterns so your shell passes the pattern to Crab. Without quotes, the shell may expand a pattern before Crab sees it.

## Add prepares the right representation

Two commands can invoke Crab’s large-file path:

- `git add` streams a tracked file through Crab’s long-running clean filter
- `crab add` processes multiple files concurrently and writes pointer blobs into Git’s object database and index

Both paths produce an index that Git can commit. `crab add` exists to improve throughput when a workload contains multiple large files.

<GitArchitecturePlayer story="add" />

### Ordinary files remain ordinary Git blobs

For `src/train.py`, Git already has the right representation. You stage it with `git add`, so it stays entirely within Git’s object model.

Git hashes the complete file, writes the blob to `.git/objects`, and updates the index. A later commit records the blob through a tree. Crab does not create chunks, xorbs, or shard metadata for this file.

This distinction also reduces push work. When pointer discovery finds no Crab pointers, the push skips the file and chunk indexes needed by the large-file lane.

### Tracked large files stage bytes and publish a pointer

For `models/encoder.safetensors`, `crab add` reads the file as a bounded stream:

1. Compute the full-file BLAKE3 hash.
2. Split the file with content-defined chunking.
3. Hash each chunk and preserve its order.
4. Write new chunks and the file recipe to local staging.
5. Flush staged data before adding the pointer to Git’s index.

Crab does not load the complete model into memory. The original file also remains in the worktree, so Python, training tools, and editors continue to open normal bytes.

The representations now differ by surface:

| Surface | `src/train.py` | `models/encoder.safetensors` |
|---|---|---|
| Working tree | Complete source | Complete model |
| Git index | Complete blob | Crab pointer blob |
| Local Crab staging | Not used | Ordered chunks and file recipe |
| Commit tree | Git blob | Git blob containing a pointer |

The ordering is important. Crab closes the staging boundary that owns the model chunks before it publishes the pointer to Git’s index. If staging fails, Crab rolls back the unpublished work instead of leaving a pointer to incomplete local data.

### A small change can reuse large-file content

Assume the next training run changes 300 MB inside an 8 GB model. Normal Git sees a new 8 GB blob because the file’s complete hash changed.

Crab computes content-defined chunk boundaries. Unchanged regions tend to produce the same chunk hashes, even when nearby bytes shift. During push, Crab uploads only chunks that the remote does not already contain.

Chunk reuse is exact, not approximate. Every reconstructed file must match the full-file BLAKE3 hash stored in its pointer. A hash mismatch returns an error instead of exposing corrupted bytes.

## Push makes data durable before changing the branch

After `git commit`, the local commit may reference both ordinary blobs and Crab pointers. `crab push origin main` discovers the complete dependency set before it changes the remote branch.

The push plan has two lanes. The Git lane transfers commits, trees, ordinary blobs, and pointer blobs. The large-file lane transfers new xorbs and shards required by those pointers.

### A source-only push uses the Git lane

When pointer discovery finds no Crab pointers, the large-file lane is empty:

1. Resolve and validate the ref edit.
2. Acquire the destination ref lock.
3. Select reachable Git objects.
4. Build and upload immutable Git pack data.
5. Verify connectivity for the new commit.
6. Commit the ref-journal transaction.

Crab acts as a serverless Git transport in this case. Object storage contains the Git packs and metadata, but every repository object remains a standard Git object.

### A mixed push runs both lanes

When a commit contains Crab pointers, the same push performs more work:

1. Resolve every pointer to a staged recipe or a proven remote copy.
2. Check which chunk hashes already exist at the remote.
3. Pack new chunks into compressed, content-addressed xorbs.
4. Upload xorbs and the shards that locate their chunks.
5. Upload the Git pack containing both ordinary and pointer blobs.
6. Verify the complete dependency closure.
7. Commit the ref update.

Crab overlaps staged reads, compression, and uploads within bounded queues. Backpressure limits in-flight work when the network or object store cannot keep pace. Every stage finishes before Crab releases the ref lock and staging handles.

## One ordering rule prevents visible broken commits

Crab’s central push invariant is:

> **All immutable dependencies are durable before any ref moves.**

For a source-only repository, the new commit stays hidden until its Git pack is durable and its reachable graph passes connectivity checks.

For a repository with Crab pointers, the same rule covers every referenced xorb and shard. A local cache can suggest that content exists, but only canonical remote storage can prove durability for publication.

The final visibility operation is a ref-journal transaction bound to the expected old ref state. Per-ref locks serialize writers to the same branch. Expected-old checks reject stale writers instead of overwriting a teammate’s push.

After the commit, a compactor folds journal transactions into a bounded manifest snapshot. File indexes and exact object locators can be repaired later because they accelerate reads. They do not define whether the visible ref is valid.

This ordering gives each failure point a predictable result:

| Failure point | Result visible to readers |
|---|---|
| Before an immutable upload | The old ref remains visible |
| During xorb, shard, or pack upload | The old ref remains visible; later garbage collection can remove unreferenced objects |
| During dependency verification | Crab rejects the push and keeps the old ref |
| During a conflicting ref transaction | Crab rejects or replans the stale edit |
| After the ref commit, during derived indexing | The new ref remains valid; repair can rebuild acceleration metadata |

A visible pointer should never name missing content. Crab checks this property at the publication boundary instead of relying on later repair.

## Clone and hydrate reconstruct the files you need

A collaborator starts with a Crab-aware clone:

```bash
crab clone crab://company-repos/vision-search
cd vision-search
crab status
```

The clone contains complete Git history and the committed pointer identities. Large files may remain as pointers until the collaborator requests their bytes.

Hydrate only the files needed for the current task:

```bash
crab hydrate models/encoder.safetensors
crab hydrate 'datasets/**'
```

Hydration follows a verified read path:

1. Read the pointer from the Git worktree state.
2. Resolve the file recipe through shard metadata.
3. Plan coalesced byte-range reads from the required xorbs.
4. Download missing ranges from object storage or reuse the local cache.
5. Reassemble chunks in their original order.
6. Verify the complete file’s BLAKE3 hash.
7. Replace the pointer atomically with the verified file.

<GitArchitecturePlayer story="hydrate" />

Applications never need to understand pointers, chunks, or xorbs. After hydration, `models/encoder.safetensors` is an ordinary file with the original bytes. If reconstruction or verification fails, Crab returns an error and does not expose a partial result.

### Dehydrate clean files to recover disk space

After a training or evaluation job finishes, replace clean full files with their pointers:

```bash
crab dehydrate models/encoder.safetensors
crab dehydrate 'datasets/**'
```

Crab skips files with uncommitted changes. It verifies clean content and performs an atomic replacement, while the durable chunks remain in object storage. You can hydrate the same files again later.

Hydration state is local. Your teammate can keep the model hydrated while your laptop keeps only its pointer. Both worktrees still refer to the same committed file identity.

## Object storage changes the scaling boundary

A conventional Git host places a repository filesystem behind a service fleet. Every serving replica must access or reconstruct that repository state. Large binary history increases the data each replica must account for.

Crab assigns the work differently:

- Clients hash, chunk, pack, upload, and reconstruct content
- Cloud object storage keeps immutable Git packs, xorbs, shards, and segmented metadata
- Per-ref locks and expected-old checks coordinate concurrent writers
- Metadata compaction keeps read indexes bounded
- Idle repositories consume stored objects without an always-on Crab data server

This design scales client work independently. Separate clients can upload unrelated branches or hydrate unrelated files without routing every byte through one Crab service process.

Object storage still imposes limits. Updates to one hot ref must serialize because Git requires an ordered result. Request latency, range-read fan-out, metadata size, and storage request budgets also affect performance.

Crab keeps those constraints on narrow surfaces. Coalesced range reads reduce request fan-out. Bounded queues control memory and concurrency. Immutable objects let readers cache data without coordinating cache invalidation for each file byte.

## Each layer answers a smaller set of questions

The two-path model remains understandable because each layer owns a defined contract.

Git answers:

- Which commit does this branch identify?
- Which paths changed in a commit?
- Which ordinary blobs are reachable?
- Which pointer identity changed between two versions?

Crab answers:

- Which file does this pointer identify?
- Which ordered chunks reconstruct the file?
- Which chunks already exist at the remote?
- Which xorb byte ranges should a reader fetch?
- Does the reconstructed content match its full-file hash?

Object storage answers:

- Is this immutable object durable?
- Does the ref still match the expected old value?
- Which committed journal generation is visible?

No layer needs to understand every implementation detail. The boundary contracts provide the proof needed by the next operation.

<TakeawayBox title="One mental model">
Use Git history for every path. Let Crab choose the storage representation for tracked large files. Treat the ref update as the moment both data paths become one visible repository state.
</TakeawayBox>

The first-time setup commands establish shared tracking rules:

```bash
crab configure s3://company-repos/vision-search --no-auto-track
crab track '*.safetensors'
crab track 'datasets/**'
git add README.md src/
crab ship models/ datasets/ -m "Add the first training snapshot"
```

The daily reviewable workflow keeps normal and large changes in one commit:

```bash
git add src/
crab add models/ datasets/
git diff --cached --stat
git commit -m "Update training data and encoder"
crab push origin main
```

A collaborator hydrates only the content required for current work:

```bash
crab clone crab://company-repos/vision-search
cd vision-search
crab hydrate models/encoder.safetensors
crab hydrate 'datasets/**'
```

Remember four points:

1. `.gitattributes` selects which paths use Crab.
2. Git commits a pointer for tracked large files and complete blobs for ordinary files.
3. Push uploads every immutable dependency before it updates the branch.
4. Hydrate reconstructs and verifies full bytes only where you need them.

The baseline fraud model uses learning rate `0.05` and maximum tree depth `8`. The team wants to evaluate nine combinations without repeatedly editing `params.yaml` or overwriting the current model.

Crab experiments start from `HEAD`, apply declared overrides in a temporary worktree, execute the DAG, and record parameters, stage hashes, metrics, and the base commit.

The displayed scores are illustrative. Your experiment records come from the metrics generated by your workflow.

## Commit the baseline first

```bash
crab run --validate
git status --short
git add crab.yaml crab.lock params.yaml src/ metrics/
git commit -m "record fraud model baseline"
crab exp save -n baseline
```

Temporary worktrees isolate experiment files from the current workspace, but their starting point is still the committed baseline.

## Run two named candidates

```bash
crab exp run \
  -S train.learning_rate=0.01 \
  -S train.max_depth=4 \
  -n lr-0-01-d4 \
  --json

crab exp run \
  -S train.learning_rate=0.05 \
  -S train.max_depth=8 \
  -n lr-0-05-d8 \
  --json
```

Inspect and compare before bringing any files into the workspace:

```bash
crab exp ls
crab exp show lr-0-05-d8 --json
crab exp diff lr-0-01-d4 lr-0-05-d8 --json
```

Use human names for exploration and the immutable experiment IDs returned in JSON for automation.

## Queue the full Cartesian product

Two repeatable `-S` flags with comma-separated values create nine tasks:

```bash
crab exp queue \
  -S train.learning_rate=0.01,0.05,0.10 \
  -S train.max_depth=4,8,12 \
  -m "fraud model learning-rate and depth sweep" \
  --json
```

Start bounded local workers:

```bash
crab queue start --jobs 2
crab queue status --json
```

`crab queue` is a local workstation or CI-runner scheduler, not a distributed cluster scheduler. On GPU machines, choose a job count that matches the training script's device allocation.

## Operate tasks by ID

Use the task IDs from queue status:

```bash
crab queue logs <task-id>
crab queue kill <task-id>
crab queue remove --failed
```

For planned shutdown, stop workers gracefully instead of killing active tasks:

```bash
crab queue stop
crab queue status
```

Keep failure logs until you understand whether the problem came from code, input materialization, resources, or a parameter combination.

## Select a result deliberately

After the queue finishes:

```bash
crab exp ls
crab exp show <winner-id>
crab exp diff baseline <winner-id>
```

Apply a completed snapshot when you want its files in the current workspace:

```bash
crab exp apply <winner-id>
```

Create a branch boundary when the candidate needs normal Git review:

```bash
crab exp promote <winner-id> --branch experiments/fraud-candidate
```

Inspect the exact subcommand behavior before choosing between apply and promote: applying changes workspace files; promoting creates a Git branch boundary.

## Share and clean up

Experiment metadata is local until pushed:

```bash
crab exp push <winner-id>
```

A reviewer can then retrieve and inspect it:

```bash
crab exp pull <winner-id>
crab exp show <winner-id>
```

After preserving selected results:

```bash
crab exp remove old-candidate
crab exp gc --keep 100 --dry-run
crab exp clean
```

<SystemNote title="Experiments are not artifact promotions">
  An experiment records an isolated run. Applying it changes workspace files,
  and promoting it creates a Git branch. A workflow artifact version captures
  clean model bytes; an artifact stage label such as `production` selects one
  immutable version. Those boundaries are intentionally separate.
</SystemNote>

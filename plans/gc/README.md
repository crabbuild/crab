# Current GC Hardening Roadmap

Generated by the `improve` skill on 2026-08-22 from commit `ff7792a4`.
This is a standalone delivery track for the GC implementation that exists
today. It targets the current Unified repository layout, current manifest and
history roots, current `.crab/ref-registry`, current shard/xorb format, and the
direct/protected/active-active writer paths already in the repository.

This roadmap has no dependency on `plans/001-pb-contract-and-baselines.md`
through `plans/010-provider-qualification-v1-cutover.md`. Do not import unimplemented
partitioned metadata, recipe trees, layout descriptors, or migration behavior
into these plans. A future layout must later implement the hardened GC
contracts; it is not needed to deliver them for current repositories.

## What current code already provides

Do not rebuild these capabilities:

- Repo GC enumerates `packs/`, `metadata/`, `manifests/`,
  `workflow/artifacts/`, and `refs/crab/artifacts/`; shared xorbs/shards remain
  bucket-owned (`crab/src/cmd/gc/mod.rs:39-45`).
- Reachability covers the current manifest, segmented pack/shard metadata, ref
  journals, workflow/artifact roots, and every validated historical manifest
  (`crab/src/cmd/gc/mod.rs:800-1071`).
- Destructive repo GC has bounded concurrent deletes and returns
  `CRAB-E0322` with partial-success counters (`crab/src/cmd/gc/mod.rs:707-776`).
- Destructive repo and bucket GC take renewable repository-maintenance leases;
  bucket GC requires a schema-current complete ref-registry and active-active
  coordinator proof (`crab/src/maintenance.rs`,
  `crab/src/cmd/gc/bucket.rs:121-168`).
- Bucket GC uses the current ref-registry plus current and historical manifests,
  adaptively enumerates global fan-out namespaces, verifies referenced shards,
  derives live xorbs/files, and tombstones stale file-index rows
  (`crab/src/cmd/gc/bucket.rs:169-327`).
- The focused in-memory GC suite passed 84 tests at the planning commit. It
  already covers grace/force, history/workflow roots, registry completeness,
  coordinator protection, adaptive listing, cancellation during enumeration,
  and maintenance-lease contention.

## Current adoption blockers

1. GC maintenance leases do not exclude ordinary push or repack writers. Age is
   the only protection for repo-local objects uploaded before manifest publish.
2. Repo and bucket enumeration plus reachability are collected into complete
   `Vec`/`HashSet` structures, so memory grows with the namespace and retained
   history.
3. Bucket deletion has no durable run/outcome journal. A first error can hide
   sibling successes, leaving only a manual rerun.
4. Bucket GC downloads every referenced shard body on every run to derive live
   xorbs and file hashes.
5. Current provider inventory parsers are cost summaries, not deletion-safe:
   malformed rows can be skipped and invalid sizes become zero.
6. No retained real-provider, long-writer, process-death, or high-cardinality
   qualification exists.
7. CLI policy is inconsistent: the command defaults to `1h`, config defaults
   to 24h, bucket force lacks repo force's confirmation path, and web docs state
   both interpretations.

## Architecture decisions for this track

- Current Unified manifest/ref-registry/history roots remain authoritative.
  Do not introduce a new repository layout or alternate reconstruction truth.
- All current writers to GC-managed namespaces participate in durable shared
  admission from before upload/adoption through publication. GC takes exclusive
  admission only for one bounded re-mark/delete batch.
- `--force` may bypass object age only. It never bypasses writer admission,
  registry completeness, coordinator proof, root revalidation, history roots,
  or crashed-writer quarantine.
- One engine owns repo and bucket mark/join/journal/execute/resume. Live LIST and
  provider inventory are candidate-source adapters, not separate collectors.
- Planning and deletion are separate. Plain GC seals a reviewable plan;
  destructive execution names that sealed run and records every outcome.
- Memory, scratch, open files, and request concurrency have explicit hard
  budgets. A streaming API that returns a complete namespace collection is not
  bounded.
- Shard closures are immutable derived GC metadata tied to current shard roots.
  They never replace shards or become file reconstruction authority.
- Canonical v1 repositories have verified closure coverage from genesis.
  Destructive GC fails closed on incomplete coverage; there is no backfill or
  permanent full-shard fallback.
- Provider inventory support begins with strict Parquet reports for current
  repo/global prefixes. Live LIST remains an explicit current-layout source;
  the two never silently fall back to each other.

## Delivery boundaries

- Plan 001 can ship first. It closes the correctness race and policy drift
  without waiting for the scale engine.
- Plan 002 is the canonical execution refactor. Do not start inventory work or
  add another delete path before it lands.
- Plan 003 changes the canonical v1 ref-registry/derived-object contract and
  requires complete coverage from genesis. Pre-cutover development repositories
  are reinitialized; no backfill is retained.
- Plan 004 is an adapter phase over Plans 002/003. A provider remains
  unsupported for destructive inventory GC until its strict fixtures and live
  evidence pass.
- Plan 005 is the standalone release gate. Passing unit tests alone does not
  qualify destructive GC for production scale.

## Standalone release acceptance

All of the following must be retained as machine-readable evidence:

- Direct, protected, and active-active pushes plus repack survive destructive
  repo/bucket GC races, including a writer longer than grace and force planning.
- No current, historical, workflow, artifact, grace, quarantined, or
  coordinator-protected object is deleted.
- Enumeration/root failure produces no executable run. Root or admission drift
  before a batch retains/replans instead of deleting stale candidates.
- Peak engine-managed RAM, scratch, open files, and requests stay within the
  configured budgets for input at least 10x larger than available RAM.
- Process death, cancellation, transient errors, and terminal partial deletes
  resume to exactly one durable outcome per candidate.
- Complete closure coverage causes zero referenced-shard body GETs during
  bucket GC; missing/corrupt closure coverage fails closed.
- Inventory-backed GC performs no recursive namespace LIST and pins one strict,
  complete, scope-matched report identity.
- Post-run fsck plus fresh clone/hydrate produces byte-identical data.
- Each advertised provider has a passing real-service row; emulator evidence is
  supplementary and clearly labelled.
- CLI help, configuration, JSON/JSONL schemas, recovery docs, and both web GC
  pages state one grace/force/plan/execute contract.

## Findings considered and rejected

- Integrating local `git gc`: local pack housekeeping does not prove remote
  object reachability, writer admission, provider completeness, or delete
  recovery. Keep remote repack separate.
- Raising grace alone: it reduces probability but cannot protect an arbitrarily
  long writer, and current force bypasses age entirely.
- Raising LIST/DELETE concurrency: it does not bound memory or make partial
  deletion resumable; it may increase provider throttling.
- Holding the existing repository-maintenance lease for the whole push or whole
  GC run: correct but turns long collection into a writer outage. Fence only a
  bounded re-mark/delete batch.
- Re-reading every shard forever: correct but makes recurring read I/O
  proportional to all retained data. Use verified derived closures present
  from canonical v1 repository genesis.
- Reusing permissive cost-report parsers for deletion: malformed/skipped rows
  are acceptable for estimates, not destructive authorization.
- Waiting for a future layout before fixing GC: the safety, memory, failure,
  provider, and qualification blockers all exist in current production paths
  and can be delivered independently.

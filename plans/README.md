# Current GC Hardening Roadmap

Generated by the `improve` skill on 2026-08-22 from commit `b738f3b2`.
This is a standalone delivery track for the GC implementation that exists in
the current Unified repository layout. It does not depend on the PB plans under
`plans/001-pb-contract-and-baselines.md` through
`plans/010-migration-provider-rollout.md`; those plans describe behavior that is
not an input to this track.

## Current implementation boundary

- Repo GC owns repo-local `packs/`, `metadata/`, `manifests/`, workflow
  artifacts, stage/experiment roots, and workflow cache xorbs
  (`crab/src/cmd/gc/mod.rs:39-51`).
- Shared `.crab/shards/` and `.crab/xorbs/` are bucket-owned. Bucket GC uses the
  current `.crab/ref-registry`, current and historical manifests, coordinator
  protection, adaptive two-hex listing, strict immutable shard closures, and
  generation-pinned file-index cleanup (`crab/src/cmd/gc/bucket.rs:129-510`).
- Service ACL views can use a view-local `<repo>/.crab` global prefix through
  `crates/crab-auth-server/src/view.rs:602-610`; that prefix is outside the
  current bucket-GC `.crab` scope and must not be silently folded into this
  track without its own roots and deletion contract.
- Direct pushes already acquire weighted `PushAdmissionTicket` capacity and
  keep it until canonical commit (`crab/src/git/push.rs:15179-15235`,
  `crab/src/git/push.rs:5218-5270`). Protected pushes deliberately rely on
  authenticated service admission; active-active pushes rely on the write
  coordinator. Do not replace those ownership boundaries with a client-only
  lock.
- Destructive GC now holds a renewable exclusive `GcSweepLease` across the
  full mark/plan/delete/reconcile interval. Canonical writers acquire shared
  global+repo `GcWriterLeases` before publication (`crab/src/maintenance.rs`,
  `crab/src/cmd/gc/{mod,bucket}.rs`).
- The CLI bucket path derives active-active protected keys only after that
  bucket sweep fence is held; durable journal batches also reject keys outside
  their scope namespace, and closure publication is content-addressed and
  idempotent.
- Active-active repo GC now acquires a coordinator fence and validates its
  safety snapshot; bucket GC still requires a per-repo coordinator proof but
  does not yet drain every external coordinator transaction.

## Remaining adoption blockers after this implementation pass

1. Bucket and repo destructive execution now journal bounded candidate batches
   and stream provider prefixes and reachability roots into run-owned marks.
   Pack-list records are consumed one at a time and store-only deletion no
   longer retains a process-wide deleted-key list. The current repository
   snapshot/ref-journal materializer, workflow artifact registry, bucket
   dry-run/repair paths, and closure sidecars still have bounded-but-materialized
   joins; those are the remaining memory-scaling items.
2. Planning interruption is recoverable: an unsealed run is reset and replayed
   from the original snapshot after root/policy validation. The replay is
   deterministic but currently restarts source enumeration rather than storing
   provider cursors.
3. Closure sidecars are strict, size-checked, and missing coverage fails
   closed. Closure reads are limited to a small body budget, and the explicit
   `--repair-closures` path is rerunnable, but it does not yet persist a
   coverage marker or its own durable progress journal. A sidecar is still a
   single JSON vector, so very large closures fail closed instead of being
   segmented.
4. Provider reports are cost-analysis inputs, not deletion proofs. A strict
   inventory contract and fail-closed gate now exist, but the current
   S3/GCS/Azure CSV readers still skip malformed rows and coerce invalid sizes to zero;
   the GCS CSV reader labels its result as Parquet
   (`crab/src/cost/inventory/report/s3.rs:31-108`,
   `crab/src/cost/inventory/report/gcs.rs:31-91`,
   `crab/src/cost/inventory/report/azure.rs:29-92`). No GC path consumes them.
5. Qualification now has deterministic fixture/evidence generation and a
   validator, but no retained GC race, crash-resume, high-cardinality bounded-
   memory, or real-provider GC pass has been recorded yet
   (`crab/scripts/e2e/gc_qualification.py`,
   `crab/scripts/e2e/validate_gc_evidence.py`).
6. The CLI now resolves omitted `--grace-period` from `Config::gc_grace_period`
   (24 hours by default); explicit values still work and non-force runs retain
   the one-hour minimum clamp. Provider inventory and real-scale qualification
   remain open.

Plan 001 is independently deliverable and must land before optimization work;
the implementation is safe for the current writer map but still needs the
complete writer-inventory and race qualification gates below.

adapter only after the run engine is durable. Plan 005 is the release gate and
can qualify live-list GC after Plans 001–003; its inventory-provider rows are
gated on Plan 004.

## Shared invariants

- Never delete a referenced current or historical manifest root, ref-journal
  object, workflow/artifact root, coordinator-protected object, grace-period
  object, or object covered by an unresolved writer lease.
- `--force` bypasses age only. It never bypasses admission, root revalidation,
  registry completeness, coordinator fencing, closure coverage, or a failed
  inventory/run journal.
- Object-store state is the correctness source of truth. Local temporary files
  may bound sorting, but process death must be recoverable from the durable run
  journal and must not require a particular filesystem.
- Every SlateDB/MetaDb guard opened by GC or a backfill closes on success,
  cancellation, and error. Every lease/heartbeat is released or its loss fails
  the run closed.

## Standalone release acceptance (not yet met)

- Direct, protected, active-active, repack, restripe, recovery, replication,
  workflow, and artifact writers are fenced in the current paths; the writer
  inventory and injected race proof are still required before release.
- Root drift, coordinator epoch drift, lease loss, cancellation, process death,
  transient delete failure, and partial provider listing all fail closed or
  resume idempotently with one durable outcome per candidate.
- Peak RAM, temporary bytes, open files, and provider requests stay within
  explicit budgets for a namespace at least 10× larger than available RAM.
- Complete closure coverage yields zero referenced-shard body GETs; missing or
  corrupt closure coverage refuses destructive bucket GC. Orphan closure
  sidecars are now considered bucket candidates only when their source shard is
  absent or in the same expired shard deletion set.
- Inventory-backed runs require one fresh, complete, scope-matched, strictly
  parsed report identity and perform no recursive LIST.
- Post-run fsck and fresh clone/hydrate prove byte-identical data.
- CLI help, config, JSON/JSONL output, architecture docs, web docs, and
  recovery/runbooks describe one grace/force/plan/resume contract.

## Findings considered and rejected

- Raising grace alone: it cannot protect a writer longer than grace and is
  explicitly bypassed by current `--force`.
- Increasing LIST/DELETE concurrency: it raises provider pressure without
  bounding memory or making partial deletion resumable.
- Holding `repository-maintenance` for an entire long push or GC run: correct
  but an avoidable writer outage; use a renewable bounded sweep fence.
- Reusing the cost inventory `Inventory` type for destructive authorization:
  its permissive skip/zero semantics are appropriate for estimates, not deletes.
- Importing PB layout/recipe/partition assumptions: they are not current GC
  roots and would make this delivery untestable against the current store.

## Large-repository scale track

`006-large-repository-scale-roadmap.md` is a separate P1, high-risk delivery
track for Kubernetes-scale Git history and team fanout. It covers bitmap
reachability, delta-preserving response packs, a generation-bound object
catalog, split commit graphs, bounded geometric maintenance, stale-pack
retention, and concurrency qualification. Its implementation is in progress;
the roadmap records completed code separately from pending Kubernetes/RustFS,
fault, provider, and canary acceptance evidence.

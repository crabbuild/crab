## Design Context

### Users

Crab is for developers, ML and data engineers, infrastructure teams, and
technical decision makers who need to understand, evaluate, and operate
large-file Git workflows without running dedicated LFS servers. They may be new
to object-storage-backed repositories, but they already understand Git. The
first-run “aha” moment is a configured repository whose large files can be
committed and pushed without learning Crab's internal architecture.

### Brand Personality

Technical, transparent, and practical. Crab should feel like a capable, calm
extension of Git. The interface creates confidence through clear sequencing,
concrete diagrams and examples, and plain language.

### Aesthetic Direction

Use a restrained product-engineering style: crisp information hierarchy,
readable technical diagrams, purposeful color, and dense but digestible
layouts. In the terminal, use task-oriented headings, aligned command
descriptions, restrained semantic color, and readable plain-text fallbacks.
Avoid marketing-heavy education pages, decorative visual noise, and generic
dark-neon developer styling. Preserve `NO_COLOR`, non-interactive, and
machine-readable behavior.

For interactive architecture diagrams, use disciplined slate surfaces,
sky/Xet cyan, Git orange, and violet for control-plane decisions. Inter carries
narrative content and Geist Mono carries commands, stages, invariants, and
system state. Motion explains state changes only; it does not decorate the
background.

### Design Principles

- Teach progressively: start with the mental model, then workflow, then internals, then operations.
- Make architecture visible with diagrams, phase labels, and flow summaries for non-obvious systems behavior.
- Keep Git muscle memory intact; organize navigation without renaming commands.
- Lead first-time users to one real success with the fewest required choices.
- Keep content scannable and reveal advanced options through contextual help.
- Preserve trust with balanced comparisons, concrete command flows, and explicit side effects.
- Respect working engineers: minimize fluff and always show the next useful action.
- Keep architecture labels, arrows, and state transitions readable at every supported width.
- Keep architecture canvases at a readable natural size and place them in responsive, touch-scrollable viewports when the page is narrower than the diagram.
